redis 集群

  • 主从

写请求全部交给主库，读请求交给从库，从库定期同步主库数据

  • 哨兵

主从模式的技术上，添加哨兵结点，哨兵结点利用心跳检测机制检测系统。如果主库宕机，哨兵自动选举一个从库升级为主库

  • 分片

多个主从节点，移除哨兵，多个主节点形策P2P网络，互相心跳检测健康。

插槽有16384个节点，每个主节点分到一些槽位。处理数据时，hash(key)对槽的数量取模，映射到槽位上，交给对应主节点处理。

redis 主从同步

分为全量同步和增量同步

redis的数据集有一个id和偏移量offset
从库向主库提出同步请求，发送从库的id和offset

  • 如果主库的id != 从库的id，则触发全量同步：

主库开启一个线程，将数据生成一个RDB，并发送给从库

在生成RDB同时，主库仍然在更新。将这部分数据额外放到一个日志repl-backlog，并发送给从库。从库收到后，清空原有数据，用RDB更新数据，然后执行repl-backlog的数据，完成同步。

  • 如果主库的id == 从库的id，则触发增量同步：

主库回复continue, 根据从库的offset和主库的offset，查询repl-backlog，将两次offset之间的命令传给从库，从库执行。

限流

限流 令牌桶

令牌桶算法是通过桶中存储令牌来进行限流，每个令牌代表一个请求。令牌以固定速率放入桶中，桶有一个最大容量，当桶满时新的令牌会丢弃。请求到来时，会从桶中取令牌，如果桶中没有令牌，则请求被拒绝。

  • 优点：
    容忍突发流量：当令牌桶中有令牌时，可以高效处理突发流量。
    支持平稳流量控制和突发流量控制。
  • 缺点：
    需要维护令牌桶的状态，可能带来一定的存储和计算开销。
    适用场景：适用于允许一定的突发流量，但同时限制平均速率的场景。

限流 漏斗算法（Leaky Bucket）

桶中的请求按固定速率处理。如果请求来的速度超过漏斗的流速，溢出的请求将会被丢弃。漏斗算法保证了流量的平稳输出。

  • 优点：
    保证了请求的流量平稳输出。
    适用于消化速率固定的场景。
  • 缺点：
    对突发请求的容忍度较低，较严格的控制机制可能导致请求丢失。
    适用场景：适用于请求输出速率固定且无法接受突发流量的场景。

实现：redis 限流

可以利用 Redis 的 INCR 命令维护请求计数，并使用 EXPIRE 设置过期时间

熔断 降级

熔断：

当系统检测到某个服务调用出现异常（如失败率超过阈值）时，熔断器会“断开”与该服务的连接，拒绝进一步的请求，直到系统恢复正常

降级：非常规应对措施

有意识地降低系统的部分功能或服务质量，以保证系统的核心功能和关键服务仍能继续正常运行

降级的实现方式

  • 开关硬编码

if (tag) {
…
}

  • AOP拦截

  • 策略/工厂设计模式

总结区别

  • 熔断是针对系统故障时进行保护，避免故障扩散。
  • 限流是控制流量，防止系统过载。
  • 降级是当系统资源紧张时，降低服务质量，保障核心功能的正常运行。

Kafka 消息丢失

Kafka：生产者->broker->消费者。broker保存topic分区，分区中保存消息。

生产者->broker: 异步发送，失败时回调处理或重发

broker存储：分区主从备份。默认的ack是主分区保存好消息后ack，想要强一致可以设置acks = all, 要求分区也保存完毕后再ack

broker->消费者：可以关闭自动提交偏移量，采取手动提交偏移量。采用同步+异步。

Kafka 重复消费

设置消息的有效key相同，这样消息会路由到一个分区，同一个分区的消息按顺序消费。

Kafka 数据清理

Kafka的分区数据保存在本地的日志文件。文件过大时，分段成多个文件存储。消息过期触发清理。也可以开启topic所占文件超过一定数值，把最早的消息丢弃。

Kafka 高性能

消息分区：topic划分为不同的分区存储在不同的broker上，可以不受限地处理更多资源。
顺序读写：Kafka消息不断追加到本地磁盘末尾，顺序读写利用页缓存提高性能
零拷贝：
原来的消息：磁盘->内核空间页缓存->用户空间kafka->内核空间socket缓冲区->网卡

零拷贝：磁盘->内核空间页缓存->内核空间socket缓冲区->网卡

不需要内核空间和用户空间拷贝，减少了用户态和内核态的切换。

核心线程数，最大线程数，阻塞队列，临时线程存活时间和单位，线程工厂，饱和策略

任务到来，如果当前工作线程是否到达核心线程数，如果不是，派发一条核心线程处理。如果核心线程都已经在工作：

如果线程数等于最大线程数，任务进阻塞队列

ThreadLocal

ThreadLocal提供线程局部变量，每个线程各自保存一个独立的变量副本。

每个线程有一个ThreadLocalMap，key是ThreadLocal，value是保存的值。

key是ThreadLocal弱引用。不能保证key不被回收。但value是强引用，不会被回收。如果出现key被回收（为null），则value不会被访问，出现了内存泄漏

可以使用remove方法，移除掉value，避免内存泄漏

登录和校验

登录状态的校验是绝大多数的请求执行前需要完成的校验，需要根据用户权限进行拦截。

  • 登录

首先登录怎么处理：

密码是md5加密后存到数据库的。用户登录，将密码传送过来，加密后和数据库对比，一致则登录成功，并且返回一段token。这个token包含有效期。

然后返回给浏览器。前端收到这个信息，缓存这个token，以后的所有请求，都携带这个token即可

  • 校验

然后不同的服务器就可以根据是否携带token，来判断是否登录，并赋予相应的权限。

因为这个token是可以包含有效期的，服务端可以校验是否过期，如果过期，返回401，跳转到登录。

  • 双token优化

问题在于：如果过期时间太长，不够安全；太短则频繁登录。

这里设置两个token，一个有效期短，accessToken，一个有效期长refreshToken。当检测到accessToken过期，会利用有效的refreshToken刷新一个新的accessToken

好处是，accessToken有效期较短，即使被盗取，攻击者能利用的时间窗口也有限

当访问Token过期时，用户可以通过刷新Token来获取新的访问Token，而不需要重新登录

  • AOP/网关拦截

由于校验操作是几乎每个服务都要执行的，因此可以考虑采用AOP的方式进行拦截。

这里我的方案则是放到网关层统一处理，利用Filter过滤器进行拦截。

文件分块上传

大文件上传问题

一个视频可能很大，上传服务器的时间可能较长。考虑上传过程中发生断网，网络不稳定，导致传输失败，那么我们可能需要重新传输整个大文件。为了解决这个问题，提高传输效率，采用分段传输，端点上传机制。

首先，明确一下，文件是由本地上传到minio服务器

流程：

1、确认上传任务，token：

前端计算出文件的md5值，这个信息上传给web服务器，由服务器创建上传任务。用id进行区分

返回内容：任务编号，分块的状态。

前端根据返回结果，进行处理：

对文件进行分块，对于每个分块：

发送（任务id,分块号），向服务端请求预前面URL，这个URL服务端向minio服务器申请。并返回给前端

前端使用这个预签名，直接将文件上传给minio服务器，不需要再经过web服务器。minio服务器返回结果。

当前端发现所有分块已经上传成功，向服务端发起合并请求（任务ID），服务端向minio检测并发起合并请求，合并分块。

这样即使中间断网，或者某些分块没有上传成功，显示失败，用户再次发起上传请求时，实际上。只需要重新上传对应的分块即可。而这些分块上传的状态都在数据库中保存。分块也可以并发上传。

搜索

视频搜索为什么要用es

视频是需要长久保存的，视频文件放minio，视频信息（视频URL，标题，简介，作者编号等）放数据库，MySQL，这没什么问题。问题在于搜索的时候不是很方便。因为我们B站搜视频，往往会输入关键字，或者作者，它往往是视频的标题的部分内容，因为我们很难记得视频完整的标题是什么。

如果只使用MySQL，那么对视频名称，或者间接字段加索引，类型是字符串。一方面，字符串它长度比较长，索引效率不算很高；另一方面，字符串的排序规则，是按照ascii码逐个排序，也就是只能支持前缀，也就是最左匹配。我们需要模糊匹配中间，或者结尾，任意地方的子字符串，只能全局的搜索了，那效率会非常的低

ES采用了倒排索引。一般我们是索引出来的编号，去找内容。ES是这样的，一个文档，先用分词工具进行分词，分成很多个比较常见的词语，然后，记录这些词语到文档id的这样一个映射表。再对这些词进行排序。这样我们搜索时，就搜索这些词就行了。同样涉及字符串排序，ES是把长字符串中，常见的词都抽取出来，我们只需要匹配其中一个词就行。而MySQL的模糊匹配，如果想利用索引，只能最左匹配。

es和MySQL怎么保持同步

分全量和增量。简单的方法是，新建一个es结点，先把MySQL中的数据，批量导入。之后，用户上传或者删除视频，先修改MySQL，再改es即可。由于一般不会发生太多人同时上传视频的情况，一般情况可以应对。但如果考虑得更完善，可以利用数据库的日志：利用订阅binlog的方式更新ES。

点赞系统

点赞系统，是有一定的并发压力的。可能很多人同时点赞。

直接放redis其实也是一种思路。我这里设计的时候，还是先用MySQL数据库存储点赞的信息。

如果直接操作MySQL, 并发量吃不消。给用户的体验也不好。因为我们对视频点赞，点赞成功后，我们的预期是前端显示的点赞数量增加，且标记你已经点赞了改视频。对于压力较大的情况，我们采用消息队列来处理：点赞消息交给Kafka, Kafka再发送给相应的模块处理。相当于一个异步的处理。

对于异步任务，前端什么时候刷新呢，这里采用websocket的机制。每当需要异步任务，会随机生成一个sessionId和taskId, 注册到websocket会话管理器。当服务端处理完成后，向会话管理器发送消息，然后就会执行注册的回调函数，刷新界面，重新读取。

实际上，这里在单机的情况下，效果可能不是很明显。实际部署的时候，可以部署到多台机器上，每台服务器管理若干视频，处理相应的点赞消息，减少压力。实际上就是水平分表。

直接使用redis也行。

websocket底层原理

单个 TCP 连接上进行全双工通信的协议，允许客户端和服务器之间实时、双向地传输数据

WebSocket 连接始于一个 HTTP 握手请求，客户端通过发送一个带有 Upgrade 头的 HTTP 请求来请求升级协议。服务器若支持 WebSocket，则返回一个带有 Upgrade 头的 HTTP 响应，完成握手

握手完成后，通信通过数据帧进行。WebSocket 帧由头部和负载组成，头部包含操作码、掩码、负载长度等信息，负载则是实际传输的数据。

通过 Ping 和 Pong 帧维持连接，Ping 帧由一端发送，另一端需回复 Pong 帧。

通过发送关闭帧（Opcode 为 0x8）来终止连接，双方在收到关闭帧后关闭 TCP 连接

协议优势

  • 低延迟：相比 HTTP 轮询，WebSocket 减少了不必要的请求头和数据传输。

  • 高效：通过长连接和二进制帧传输，减少了通信开销。

  • 实时性：支持服务器主动推送数据，适合实时应用。

缓存

这里也用到了redis，主要用于缓存信息。缓存用户信息

仿B站系统，除了视频，还有基本的用户信息管理，用户也可以修改。但每次显示都差数据库，效率不高，因此把展示的信息缓存到redis，而每次更新的时候，更新完数据库，删除缓存，等下次读的时候再刷到缓存，也就是一个旁路缓存的策略。可以一定程度地减少压力，提高性能。

创建dispatcherServlet，绑定容器context

根据（写死的）className，利用构造方法反射创建对象。参数是context容器，因为后面要找bean。

dispatcherServlet注册给servletContext

我们知道，jerry-mouse或者说tomcat, 会创建一个servletContext就是servlet容器，dispatcherServlet需要注册进去。问题是现在我们没有servletContext, 怎么办？factory.getWebserver创建webserver。

这个接口它的参数是一个数组，类型是ServletContextInitializer，实际上就是一个函数式接口，里面有一个onStartUp接口，参数是context，也就是对servletContext做一些后置操作。前面讲的context是spring的容器，存放bean; 这个servletContext是服务器（jerry-mouse）的servlet容器

这个servlet容器，注册是事情，就是要让他用addServlet方法，动态加uDispatcherServlet。这里只是add，没有注册，因为接口没有这个方法，webserver实现类中才有。

到这一步，dispatcherServlet已经被创建，并通过addServlet，动态加入到servletContext

webserver.start()启动

webserver.start()启动，这是接口。

实现方式，就是servletContext中拿到dispatcherServlet，然后需要匹配所有的路径，执行注册这个dispatcherServlet，让所有的路径，都交给这个Servlet进行处理.

然后创建一个包装的servletConfig, 执行init方法 。

init

然后执行init方法，这又是模板方法，因为DispatcherServlet是HttpServlet的子类。重写init()即可，注册就在这一步完成。

到此，解决的问题

  • 启动
  • dispatcherServlet注册给jerry-mouse
  • dispatcherServlet拿到spring的context
  • 请求通过jerry-mouse交给dispatcherServlet

一个请求过来，怎么交给controller，怎么交给method处理

jerry-mouse服务器，会执行servlet的service()方法，参数是request, response。实际上就是通过报文解析得到的request，可以通过request的接口，得到方法(GET, POST), URI, body这些数据，也就是报文的内容。

那dispatcher负责分发，那肯定要预处理，进行注册

注册

我们知道了，dispatcherServlet可以拿到spring的context, 那么，根据类型查找RestController，找到所有的BeanDefination，然后对于每个RestController，遍历它的方法，看下是否是public，以及有没有GetMapping或者PostMapping接口。有的话，继续处理

将 request方法，bean，method信息，path打包注册，交给MethodHandler注册，也就是注册到一个map里面。

HTTP请求

对于一个HTTP请求，根据url, 解析method，路径，匹配到对应的Bean和method。这里需要处理的是，路径可能有PathVariable。所以匹配方法会比较麻烦。找到后，就锁定了方法了。下面的问题是，方法的参数是怎么定的

restcontroller中，方法的参数是怎么定的

我们平时写springboot应用，一个controller,一些方法，有的参数有注解，像PathVariable, RequestParam, RequestBody，RequestHeader，RequestAttribute，SessionAttribute; 还有一些没有参数，但是类型是HttpRequest,HttpResponse, HttpSession等。它怎么来的问题。

都是request变来的。只要对于方法的每个参数，依次判断是否有注解，如果有，依次处理；没有，则判断是否是那几个类型，有的话，用request或者response的相关内容给它即可。这一块内容的处理也用了策略模式，在dispatcherServlet创建的时候就注册了相应的map

总结

所以，实际上，springmvc就是dispatcherServlet这一个servlet，在执行service()方法罢了，所有的参数，各种注解，都是从request，response里面来的。
